# Specification: APK Independent Acceptance and Handoff

## Overview

Perform the only final evidence-and-adoption acceptance review and publish the only
successor hashes consumable by the shared-kit and cartridge-rebuild tracks. No
evidence collector, mapper, truth-test author, prior phase reviewer from T2–T9,
or root coordinator may serve as final acceptance reviewer. The normal execution
requires newly spawned `fork_turns="none"`, tool-attested final-review subagents.
For this execution, the user explicitly stated Kimi agents were unavailable and
authorized one new T10-only independent reviewer. The resulting artifacts must
therefore disclose that no provider-fork, ancestry, or collaboration-tool
attestation exists rather than representing the unavailable proof as present.

The accepted handoff also binds the canonical ElvGames pack root
`packages/advantage-play-kit/assets/standard`, asset contract, generated catalog,
import/license receipts, and release version for every adopted mapping.

Passing structural tests does not establish factual correctness. This track revalidates the story from raw source and the independent denominator.

## Functional requirements

### FR1: Fresh denominator reconciliation

Re-run identity, scene/state, historical, copy, and candidate-asset reconciliation independently of synthesis.

### FR2: Claim and evidence validation

Validate 100% claim-to-evidence coverage, revisions, file/line hashes, source classes, conflicts, confidence, agent receipts, and stop-loss history.

### FR3: Cross-artifact acceptance

Check every game, scene/state, blueprint field, standardized/bespoke capability, responsive contract, concrete usage, semantic role/state, canonical standard-pack candidate key or blocked mapping, candidate disposition, gap, and unresolved decision.

### FR4: Runtime and asset evidence

Review all required browser evidence and per-candidate audit records. Sampling is forbidden for game/scene coverage, accepted reuse/adapt decisions, standardized capabilities, and ontology entries.

This does not require a second visual audit of every file in the complete standard
pack. T10 validates the bound pack contract, catalog, receipts, release, and every
selected mapping; each selected cartridge asset still requires applicable visual
and browser acceptance.

### FR5: Failure-artifact quarantine

Prove no failed monolith artifact is an accepted dependency except labeled negative evidence.

### FR6: Product acceptance and hashes

Publish the complete independent report before requesting product-owner approval. Generate SHA-256 successor inputs only after review remediation and approval.

## Acceptance criteria

- Required role receipts exist with compatible distinct agent IDs.
- Fresh denominator equals accepted coverage or all discrepancies are resolved.
- Every factual claim and derived record validates against exact evidence.
- Every contract accepted as runnable under the program definition has reviewed browser evidence.
- Every candidate path and accepted disposition reconciles; every adopted mapping
  is standard-pack-relative or explicitly blocked.
- The accepted root policy, asset contract, generated catalog, import/license
  receipts, and release version bind every adopted mapping.
- No unresolved Critical, High, or Medium finding or unknown Must-have decision remains.
- Product owner receives full artifacts and independent report, not only a summary.
- Only post-approval hashes are published.
- Successor tracks reject missing, revoked, stale, or mismatched hashes.

## Out of scope

- Fixing source games, implementing APK systems, generating assets, or rebuilding cartridges.
- Reusing final reviewers from upstream tracks.
- Performing a second per-file visual audit of the complete ElvGames standard pack.

## Accepted execution boundary

T10 may resolve an unknown Must-have by making a final fail-closed `blocked`
decision for successor consumption; it may not infer the missing value. The
accepted T11 handoff can therefore include accepted capability contracts while
approving zero runtime contracts and zero asset mappings. Browser success is not
accepted unless authentic evidence exists for the exact contract.
