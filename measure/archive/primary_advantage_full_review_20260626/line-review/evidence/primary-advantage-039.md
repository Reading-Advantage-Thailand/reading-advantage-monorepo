### LR-primary-advantage-039-001 — Initial-load progress math uses `Math.ceil(progress / (100/14))`; for tasks 4 and 13 the rounding step restores a task ahead of the user's actual position

- Severity: Medium
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/lesson-progress-bar.tsx:101-104`
- Evidence: Lines 101-104 compute `taskWidth = 100 / 14; const taskNumber = Math.ceil(data.userLessonProgress.progress / taskWidth);`. The server-side progress value is written on lines 211 and 310 as `Math.round((newTask / 14) * 100)`. The two rounding steps disagree at certain tasks because the forward write rounds `N/14*100` to an integer, then the read divides back. Worked examples:
  - `N=4`: write `round(4/14*100) = round(28.571) = 29`; read `ceil(29 / 7.142857) = ceil(4.06) = 5`. The user completed task 4 (vocabulary collection) but a page reload renders task 5 (deep reading).
  - `N=13`: write `round(13/14*100) = round(92.857) = 93`; read `ceil(93 / 7.142857) = ceil(13.02) = 14`. The user finished task 13 (language questions) but a reload jumps to task 14 (lesson summary) without ever displaying the language-questions screen.
  - All other tasks round-trip exactly (N=1 → 7 → ceil(0.98)=1; N=2 → 14 → ceil(1.96)=2; … N=7 → 50 → 7; N=8 → 57 → ceil(7.98)=8; N=10 → 71 → ceil(9.94)=10; N=14 → 100 → 14). The two values of N that misbehave (4 and 13) are not adjacent to the step boundary, so this is not a round-up ambiguity; the choice of `Math.ceil` plus `Math.round` together is the cause. The pattern is purely local to this component (other consumers of `userLessonProgress.progress` in `assignmentController.ts:319-350` round-trip via the same model).
- Impact: Medium. On reload after task 4 or task 13 the user is silently moved one phase ahead. The DB now stores a `progress` value inconsistent with the `currentTask` index actually displayed. For a primary-student app, the lesson-summary step also marks the lesson as "completed" in some downstream consumers (the `setPaused(true)` branch on lines 111-113 and 301-303 plus the `progress >= 100` threshold elsewhere), so the off-by-one on task 13 could prematurely close the lesson, prevent the language-questions chatbot from ever being reached, and leave the user with no record of completing the chatbot.
- Recommendation: Pick one rounding strategy and use it on both sides. The cleanest fix is to compute `progress = Math.ceil((N / 14) * 100)` on write (line 211 and 310) and drop the `Math.ceil` on read (replace line 102-104 with `const taskNumber = Math.round(data.userLessonProgress.progress / taskWidth);` or simpler: skip the read math entirely and have the server return `currentTask` directly). Track under a `primary_advantage_lesson_progress_round_trip_<date>` follow-up track alongside the broader `assignmentController` audit (this batch is one of several that use the same `(N/14)*100` encoding).

### LR-primary-advantage-039-008 — `nextTask` advances to `newTask = Task + 1` but writes the *post-advance* progress; a server-side failure leaves the local state ahead of the server

- Severity: Medium
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/lesson-progress-bar.tsx:249-345`
- Evidence: Line 265 reads `const newTask = Task + 1;` (the task the user is *moving to*). Line 310 writes `progress: Math.round((newTask / 14) * 100)`. If the fetch fails (line 321 `else` branch), the function logs the error (line 322-326), resets the fade/loading flags (line 327-329), and falls through. Critically, the local state has *not* been advanced: `setCurrentTask(newTask)` is only called inside the `response.ok` branch on line 316. So on failure the user sees the same phase they were on. But on success, the local state and the server progress are aligned. The bug: the `await saveArticleToFlashcard(assignment?.articleId as string)` call on line 277 (for `newTask === 7`, the multiple-choice phase, after vocabulary flashcards) is awaited inline before the progress fetch. If `saveArticleToFlashcard` throws or hangs, the user is stuck on the transition (the spinner on lines 589, 624, 657 keeps spinning because `setIsTransitioning(false)` is in the `finally` block on line 339, but `setPhaseLoading(false)` is inside the `response.ok`/`else` branches and would not be called if `saveArticleToFlashcard` threw before line 305). Reading the `try/catch` on line 262-336: a throw inside the `await saveArticleToFlashcard` would be caught by the `catch` block on line 331 and `setPhaseLoading(false)` would fire on line 336, so the UI does recover.
- Impact: Medium. The "save flashcard then advance" coupling is fragile: if the user is on task 6 (sentence collection) and clicks Next, the code sets `newTask = 7`, calls `saveArticleToFlashcard`, and only then POSTs to `/api/assignments/{id}` to mark task 7 reached. The save happens before the progress update, which is the correct ordering (don't mark the lesson advanced until the flashcard is saved), but the two calls are not transactional — if the flashcard save succeeds and the progress POST fails, the server has flashcard data without a matching progress entry. For a primary-student app the flashcard is a study artifact and the progress is the lesson ledger; the mismatch is recoverable on the next reload (`saveArticleToFlashcard` is idempotent, but the server does not deduplicate).
- Recommendation: Wrap the two side effects in a single server action or a server-side transaction. Specifically, move `saveArticleToFlashcard` into the assignment progress controller (`assignmentController.ts:319-350`) so the save and the progress update share a transaction; or move both into a server action `actions/assignment.ts:completeLessonTask(assignmentId, articleId, newTask, timeSpent)` that the client calls atomically. Track under a `primary_advantage_lesson_progress_transaction_<date>` track that also audits other places where the client chains two server calls.
