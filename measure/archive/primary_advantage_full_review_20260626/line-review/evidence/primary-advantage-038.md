### LR-primary-advantage-038-002 — Auto-complete useEffect fires before the score-incrementing `updateUserActivity` resolves; UI shows "completed" even when the server rejects the activity log

- Severity: High
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/games/lesson-vocabulary-matching.tsx:204-247`
- Evidence: The useEffect on lines 204-247 has guard conditions (lines 221-226) `vocabularyPairs.length > 0 && userMatches.length === vocabularyPairs.length && !isCompleted && hasUserInteracted`. When all matches are made, the body synchronously calls `setIsCompleted(true)` (line 232), `setShowResult(true)` (line 233), `handleComplete()` (line 234), and `setScore((prev) => prev + 1)` (line 237) — but the `updateUserActivity(articleId, ActivityType.VOCABULARY_MATCHING, UserXpEarned.VOCABULARY_MATCHING, 0, { score: ... })` call on lines 206-214 is awaited inside the inner `handleComplete` function which is **not awaited** by the useEffect body. React effects cannot be async; the body of the effect runs synchronously, then the inner async `handleComplete` is invoked (line 234) and the rest of the effect body continues. `setIsCompleted(true)` therefore runs in the same microtask as the activity dispatch, so the completion UI renders before the server confirms whether the activity was logged. The dependency array on line 248 is `[userMatches, vocabularyPairs.length, isCompleted, hasUserInteracted]` — `setIsCompleted`, `setShowResult`, `handleComplete`, `setScore`, and `t` (used in toasts on lines 238, 240-244) are not in the deps, so ESLint's `react-hooks/exhaustive-deps` rule should flag this; the rule is likely disabled or warnings are silenced in this app's lint config.
- Impact: High. A primary student who finishes a vocabulary matching set sees the celebration screen (lines 429-484) even if `updateUserActivity` returns `{ success: false }` or throws. The mismatch between perceived success and persisted state means: (1) the activity log on the server may be missing, (2) the per-user XP may not be incremented on the server, (3) the client `score` (line 237) and server XP diverge. For the Reading Advantage upstream, this same useEffect probably fires after a server action that returns success; the fork's effect decoupled the local celebration from the server result.
- Recommendation: Either (a) move the entire activity-log + completion-UI transition into a single async function called from a button (e.g., the "Complete activity" button on line 727), await `updateUserActivity`, and only then set `setIsCompleted(true)` / `setShowResult(true)`; (b) wrap the body in `startTransition` and only call `setIsCompleted(true)` inside the transition's success branch; (c) add a `pending` UI state (`isPending` from `useTransition`) and gate the celebration UI behind a successful server response. The `handleComplete` inner function (lines 205-220) should be renamed to `handleCompletionAsync` to make its async-ness explicit, and the outer useEffect should remove its now-redundant `handleComplete()` call on line 234. Add `setIsCompleted`, `setShowResult`, `handleComplete`, `setScore`, `t` to the dep array or hoist the effect body into a `useCallback` so the lint rule passes.

### LR-primary-advantage-038-005 — Biased shuffle using `(arr) => Math.random() - 0.5`; the right column may cluster identical items on one side

- Severity: Low
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/games/lesson-vocabulary-matching.tsx:179`
- Evidence: Line 179 shuffles the definitions for the right column with `const shuffled = [...pairs].sort(() => Math.random() - 0.5);`. This comparator does not satisfy the requirements of `Array.prototype.sort` (the comparator must return a consistent transitive ordering — `Math.random() - 0.5` is non-deterministic and not a total order). Modern V8 implementations of `sort` since 2019 use TimSort, which detects runs and can produce highly biased outputs when the comparator is not a total order: items near each other in the original array tend to stay near each other after the shuffle. The result is that for a primary-student vocabulary matching game, the right column often clusters words whose definitions are visually or semantically similar, making the matching task trivial for adjacent items and ambiguous for cross-cluster items. The deck-view.tsx sibling on line 188-189 uses `Object.values(VOCABULARY_LANGUAGES)` directly without shuffling, but the reading-advantage upstream likely used a Fisher-Yates shuffle.
- Impact: Low. The activity remains playable, but the matching challenge is uneven. For a primary-student app where vocabulary matching is supposed to be a learning reinforcement, the triviality of "all correct" matches in a clustered shuffle undermines the educational value.
- Recommendation: Replace the sort with a Fisher-Yates shuffle: `const shuffled = [...pairs]; for (let i = shuffled.length - 1; i > 0; i--) { const j = Math.floor(Math.random() * (i + 1)); [shuffled[i], shuffled[j]] = [shuffled[j], shuffled[i]]; }`. Add a Vitest unit test asserting that the shuffle is approximately uniform across 1000 trials (or, more practically, that no two consecutive original-order items remain adjacent in > 5% of trials).
