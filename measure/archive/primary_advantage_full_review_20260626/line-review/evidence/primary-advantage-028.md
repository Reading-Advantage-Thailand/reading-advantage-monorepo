### LR-primary-advantage-028-001 — Forgot-password form never sends a real password-reset email; API call is commented out and form unconditionally reports success

- Severity: Critical
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/auth/user-reset-pass-form.tsx:18-52`
- Evidence: The `onSubmit` handler (lines 18-52) contains a `fetch("/api/send", { method: "POST", body: JSON.stringify({ email }) })` call that is **entirely commented out** (lines 27-33), and a `sendPasswordResetEmail(firebaseAuth, ...)` call that is also commented out (lines 41-51). After the comments, line 34 unconditionally calls `setIsEmailSent(true)` and line 35 calls `setIsLoading(false)`. The success branch on lines 95-101 then renders the green "The email has been sent!" confirmation screen regardless of whether any email was actually sent. The form is the entry point from `app/[locale]/auth/forgot-password/page.tsx` (confirmed via the RSC manifest lookup: forgot-password/page imports `UserResetPassForm` from this file).
- Impact: Critical security and trust bug. A primary-age student, parent, or teacher who submits a forgotten-password request receives a "we sent you an email" confirmation but no email is ever sent. They will assume the email is in their inbox and never know their account is locked out. Worse, the form silently swallows the comment-history of the codebase (this file looks like a half-migrated firebase → first-party-port fork), and a follow-up note `// sendPasswordResetEmail(firebaseAuth, email, ...)` (line 41) reveals the prior implementation used Firebase. The `apps/primary-advantage/AGENTS.md` migration history section explicitly says auth is being migrated toward the first-party adapter pattern, but this forgot-password flow was left as dead code with a fake success path.
- Recommendation: Replace the entire `onSubmit` body with a real call to the first-party `auth` adapter (`auth.requestPasswordReset(email)` per AGENTS.md "Auth Adapter" contract) or to `POST /api/auth/reset-password` (which already exists as a route stub — see `app/api/auth/reset-password/route.ts` per the inventory batch 013). Remove the firebase comment block (lines 41-51). Add Zod validation for `email` at the form boundary and rate-limit the endpoint server-side per the root AGENTS.md "Rate limiting for login endpoints" requirement. Until the real integration ships, the form should at minimum call `await fetch("/api/auth/reset-password", { method: "POST", body: JSON.stringify({ email }) })` and only call `setIsEmailSent(true)` after `response.ok` (mirroring the pattern in `change-username-form.tsx:50-67`).

Even if the hardcoded data is replaced with real fetches (per LR-028-012), the trend lines will still say "+12% from last week" regardless of actual data. For a primary-student admin dashboard used in parent-teacher conferences, presenting fake trend numbers alongside real totals is a credibility bug — an attentive admin will notice the totals changing while the trends do not.
- Recommendation: Compute the deltas from real data. Either (a) accept a `previousWeekData` prop and compute `((current - previous) / previous * 100).toFixed(0) + "% from last week"`, or (b) have the server return the deltas as part of the activity endpoint response (preferred — keeps the calculation in the backend). Replace lines 240-243, 258-261, 278-281, 296-299 with `{t("fromLastWeek", { delta: computedDelta })}`. Add a unit test that asserts the deltas are not literal strings (a Vitest snapshot or a simple `expect(component.text()).not.toContain("+12% from last week")` after data change).
