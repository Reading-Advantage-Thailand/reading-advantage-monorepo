### LR-primary-advantage-034-001 — `update({ user: { ...session?.user } })` references undeclared `session`; runtime ReferenceError blocks XP recording on completion

- Severity: Critical
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/games/lesson-sentence-matching.tsx:206-222`
- Evidence: Inside the auto-complete `useEffect` (line 206), the inner `const handleComplete = async () => { ... }` declared on line 207 calls `updateUserActivity(...)` on lines 208-216 and then `update({ user: { ...session?.user } })` on lines 217-221. The `useSession()` import on line 42 is destructured on line 82 as `const { user } = useSession();` — `session` and `update` are **never** declared in this component's scope. The `useSession()` return type in `apps/primary-advantage/node_modules/@reading-advantage/auth-client/dist/index.d.ts:47-51` is `{ user: AuthUser | null; isAuthenticated: boolean; isLoading: boolean }` (no `session`, no `update`). The optional-chained `session?.user` is a JavaScript `ReferenceError`, not a TypeScript no-op — `session` is undeclared, so any attempt to read it throws `ReferenceError: session is not defined`. This is the **same** anti-pattern that primary-advantage-033 finding 001 documents in `lesson-sentence-flashcard.tsx:230-234`, and the reviewer explicitly listed `lesson-sentence-matching.tsx:219` as one of the 7 sibling files in `apps/primary-advantage/components/lesson/games/` that share the regression. The seven files are: `lesson-vocabulary-flashcard-card.tsx:238`, `lesson-sentence-order.tsx:306`, `lesson-sentence-order-word.tsx:288`, `lesson-sentence-matching.tsx:219` (this file), `lesson-vocabulary-matching.tsx:217`, `lesson-sentence-cloze-test.tsx:526`. The fork's lesson-games components were never updated to the slimmed-down `useSession` shape; the prior Reading Advantage implementation likely used an `useSession()` that returned `{ session, update }` (the auth-client provider code previously read `data.session?.user` from a fetch response).
- Impact: Critical. The success path of the completion handler is unreachable in a working state — the `ReferenceError` thrown by `update({...})` aborts the rest of the inner `handleComplete` callback. `setGameState(GameState.Completed)` on line 148 still runs (it is in the outer `handleComplete` shadow on line 147, called from line 236), so the user reaches the completion screen, but the `updateUserActivity` server action on lines 208-216 has already executed and its XP grant is recorded against the articleId — yet the React state update propagation is interrupted by the exception. For primary students this means XP for the activity is double-counted (or lost) depending on how the server action handles the mid-flight error, and a `ReferenceError` is logged on every completion (visible in the browser console and Sentry-style error sinks). The same bug affects 6 other game files, so a single PR fix can sweep them all.
- Recommendation: Replace `update({ user: { ...session?.user } })` on lines 217-221 with either (a) `update({ user })` (the `useSession()` return value is the correct source — note `user` is currently destructured but unused, see finding 004, so the destructure on line 82 can stay) or (b) delete the call entirely and rely on the `updateUserActivity` server action (line 208) for the authoritative state update. The auth-client package should be expanded to expose an `update()` action (or the call removed) so the surrounding 7 files can be patched in one mechanical change. Track this under a new `primary_advantage_session_update_bug_<date>` Measure track for a sweep across all 7 files.

### LR-primary-advantage-034-002 — Completed screen renders three hardcoded literals (`20` XP, `5/5` pairs, `count: 1`) instead of the user's actual data

- Severity: Medium
- Fork-divergence category: Fork-specific regression
- File: `apps/primary-advantage/components/lesson/games/lesson-sentence-matching.tsx:435-490`
- Evidence: The `GameState.Completed` JSX branch (lines 435-490) renders a stats grid (lines 465-482) with two hardcoded values: line 468 shows `<div ... >20</div>` for `xpEarned`, and line 476 shows `<div ... >5/5</div>` for the `completed` count. Line 457 calls `t("complete.subtitle", { count: 1 })` with a hardcoded `count: 1`. None of these values are derived from the actual session data: `vocabularyPairs.length` (which holds the total pairs, available on line 70-72), the `userMatches.filter((m) => m.isCorrect).length` (available on line 229-231, and used on lines 506, 683, 682-684), or the XP actually granted by `updateUserActivity` on line 211 (`UserXpEarned.SENTENCE_MATCHING` enum value). The `score` state declared on line 85 is incremented by 1 on line 239 inside `isAllCorrect` but is never read anywhere in the JSX.
- Impact: Medium. A primary-student user who completes the game with 0/5 correct (a "try again" toast on line 242-247) is then shown the same celebration screen as a user who got 5/5 correct. The `5/5` and `20` are placeholders that survived from a template; the `count: 1` ignores the per-user `count` value from the i18n catalog. For a primary-student app where the completion screen is the primary motivation loop, showing a static "perfect run" UI for every completion removes the learning signal — students cannot see whether they actually learned. The mismatch also breaks the trust contract: a parent viewing the dashboard sees one XP value in the activity log (from the `updateUserActivity` call on line 208-216) and a different value on the completion screen.
- Recommendation: Replace line 457 with `t("complete.subtitle", { count: userMatches.filter((m) => m.isCorrect).length })` (matches the rendering on line 506 and 683-684). Replace line 468 with `{UserXpEarned.SENTENCE_MATCHING}` to expose the actual granted XP, or compute a per-match XP (`Math.round((correctCount / vocabularyPairs.length) * UserXpEarned.SENTENCE_MATCHING)`). Replace line 476 with `${userMatches.filter((m) => m.isCorrect).length}/${vocabularyPairs.length}` to match the format used on lines 506-508. This finding pairs with finding 003 (XP is always granted in full) and finding 009 (`score` is incremented but unused) — all three stem from the same template-skeleton-without-data-flow pattern.

### LR-primary-advantage-034-003 — Full XP granted on every completion regardless of correctness; primary-student motivation loop detached from learning outcome

- Severity: Medium
- Fork-divergence category: Primary-student adaptation risk
- File: `apps/primary-advantage/components/lesson/games/lesson-sentence-matching.tsx:208-216`
- Evidence: The inner `handleComplete` (line 207) calls `updateUserActivity(articleId, ActivityType.SENTENCE_MATCHING, UserXpEarned.SENTENCE_MATCHING, 0, { score: UserXpEarned.SENTENCE_MATCHING })` on lines 208-216. The third positional argument (XP amount) is always the full `UserXpEarned.SENTENCE_MATCHING` enum value, and the `score` metadata on line 214 is also always the full amount. The auto-complete effect on lines 206-250 fires when `userMatches.length === vocabularyPairs.length && hasUserInteracted` (line 223-228) — it does **not** check `isAllCorrect`. The `correctCount` and `isAllCorrect` variables (lines 229-232) are only used to choose which toast to show (lines 238-247), not to scale the XP. A user who matched all 5 pairs incorrectly (5/5 wrong) still earns the full `UserXpEarned.SENTENCE_MATCHING` XP.
- Impact: Medium. Primary-student adaptation risk. The completion XP is the primary motivation lever in this app's gamification layer (per the AGENTS.md "Primary-student adaptations" concern about "age-appropriate UX"). Awarding full XP for an all-wrong run creates a perverse incentive: students can spam the activity for XP without learning. This pattern is plausible as a copy-from-Reading-Advantage mistake — the parent app presumably assumes adult or higher-CEFR learners who will self-correct, but for primary students (typically A0-A1 CEFR) the explicit reward schedule is more impactful. The "try again" toast on line 242-247 (`t("results.tryAgain", { correct, total })`) is the only signal that learning did not occur.
- Recommendation: Either (a) scale XP by accuracy: `const xp = Math.round((correctCount / vocabularyPairs.length) * UserXpEarned.SENTENCE_MATCHING);` and pass `xp` to both the third positional argument and the `score` metadata, or (b) keep the full XP but document the intentional design choice in `apps/primary-advantage/AGENTS.md` under a new "Primary-student XP schedule" section. Option (a) is preferred for educational integrity. Also gate the `setGameState(GameState.Completed)` on line 148 inside the `isAllCorrect` branch (or add a separate `Retry` state) so the celebration screen only shows on full success.

- Recommendation: If the auth-client package is expanded to expose an `update()` method (per finding 001) and the call on line 217-221 is rewritten to `update({ user })`, then `user` becomes live and the destructure is justified.
