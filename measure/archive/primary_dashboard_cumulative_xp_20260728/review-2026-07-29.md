## 3. Code quality observations

Genuinely better than what it replaced: pure function, no hidden mutation of the caller's `DateRange`, `readonly` inputs, documented. Nits, in rough order of value:

- **i18n gap (inherited, not a regression).** `DAYS_OF_WEEK` at `:13` is hardcoded English, and the JSDoc at `:7` calls it a "Localized short day label" — it isn't. The host component already pulls `useLocale()`/`useTranslations()` (`user-activity-chart.tsx:72-74`), so non-English locales render `"Fri 3"`. The doc comment overstates what the code does.
- **Redundant work in the hot path.** `:44` calls `startOfDay(new Date(...))` before `sameDay`, but `sameDay` compares via `toDateString()`, which ignores time — the `startOfDay` call allocates a Date and does nothing. The loop is also O(days × logs) with two array allocations per day; fine at current volumes, wasteful for a year-long range.
- **`const day` in a mutated `for` head** (`:42`) is legal but unusual; the loop variable doubles as the label source. Readable, but a reviewer will pause on it.
- **DST edge.** Advancing with `setDate` from local midnight drifts the wall-clock hour in zones where a DST transition skips midnight, which can shift the `day <= lastDay` boundary by an hour. Project TZ is +07 (no DST), so low priority — but the module is app-generic.
- **Test coverage is thin at the edges.** No case for empty `logs`, `undefined` calendar value, `to < from`, or logs dated *after* the range (which should be excluded). The two tests cover exactly the two plan bullets and nothing more.
