## Notes

- **`lib/ai/` is the only adapter module that fails 1.6.** It is also the only module in `lib/` that imports a provider SDK, and it imports three of them (`ai`, `@ai-sdk/openai`, `@ai-sdk/google`).
- The platform/cache layer (Redis, rate-limit, session-cleanup) does it correctly: it defines an interface, the implementation is selected by env (`REDIS_URL`, Upstash vs node-redis detection in `redis-client.ts:70–87`), and the in-memory fallback is also interface-conformant. This is a working model that `lib/ai/` should mirror.
- Provider selection in `lib/ai/` is partially env-driven (API-key presence gates whether the client is constructed) but it is not interface-driven — there is no `AIClient` interface that `recommendation-service.ts` or `image-generator.ts` consumer programs against. The `resolveModel()` function in `recommendation-service.ts:63–76` branches on the model-id string rather than on an injected client. This is a "switch on string" anti-pattern, not an adapter pattern.
- A shared `@reading-advantage/ai` package would resolve 1.1, 1.3, and 1.6 simultaneously and align `science-advantage` with the other apps.
- No storage or email feature is actually live in this app, so 1.2 and 1.4 are N/A. If storage is added in the future, the absence of `lib/storage/` plus the env vars already declared in `.env.example` will become a §2.3 / §1.2 latent debt.
