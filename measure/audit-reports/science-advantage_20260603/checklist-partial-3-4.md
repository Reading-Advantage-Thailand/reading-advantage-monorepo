## Section 4 — Authentication & Authorization

| 4.2 | Auth adapter only (no `getServerSession`, cookie/header reading) | **PASS (with one sub-finding)** | `rg 'getServerSession' apps/science-advantage/` returns 0 source-code hits (only 2 hits in `docs/archive/architecture/*.md`). `rg 'cookies()' apps/science-advantage/` returns 3 hits, all in `apps/science-advantage/lib/auth/session.ts:94, 108, 116` -- and all of them set/get the `SESSION_COOKIE_NAME` exported from `@reading-advantage/auth` (lines 9, 95, 109, 117). `rg 'headers()' apps/science-advantage/` returns 1 hit in `next.config.ts:27` (Next.js `headers()` config for response security headers -- not a session read). ## Pass / fail summary

| Section | Total checks | PASS | FAIL | PASS-with-caveat |
|---------|-------------:|-----:|-----:|-----------------:|
| 3 (Backend-as-Code) | 5 | 1 | 3 | 1 (3.2) |
| 4 (Authentication) | 9 | 5 | 2 | 2 (4.2 sub, 4.6 sub) |

**Section 3 headline:** the domain layer exists and uses the `assertCan` pattern, but the per-module structure is a single `index.ts` file -- no `schema.ts`/`contracts.ts`/`queries.ts`/`mutations.ts`/`actions.ts`/`permissions.ts`/`errors.ts`, no Zod input/output schemas, no `command()` wrapper usage.

**Section 4 headline:** the auth surface (proxy.ts, login rate limit, password hashing) is mostly adapter-driven, but **the app's own `bcryptjs` usage bypasses the auth package**, **no audit log infrastructure exists anywhere in the monorepo**, and **handler-level authorization is hand-rolled `role === '...'`** instead of using `assertCan`/`roleAtLeast` from the centralized permission system.
