## Findings

### F-SA-B32-001 — Divergent/duplicate LessonContent schema in `convert-md-to-structured.ts` produces output incompatible with canonical schema
- **Severity:** High
- **File:** `scripts/convert-md-to-structured.ts:43-66, 136-202, 255-272`
- **Detail:** This script re-declares its own `MaterialItem`, `MaterialsBlock`, `ProcedureStep`, and `ProcedureBlock` interfaces that **diverge from the canonical schema** in `lib/schemas/lesson-content.schema.ts`:
  - It emits materials as `{ name, notes }` (lines 153-156), but `MaterialItemSchema` requires `item` (and optional `quantity`/`itemThai`); `name`/`notes` are not in the schema and `item` is missing → `validateLessonContent` would **reject** these blocks (line 95 of schema: `item` is required).
  - It emits procedure steps as `{ step, instruction }` (lines 178-181), but `ProcedureStepSchema` requires `stepNumber` (schema line 103). The `step` field would fail and `stepNumber` would be missing.
  - It never extracts `quantity`, whereas the canonical/golden output does (see fixture `golden-lesson.expected.json:48-58`).
- **Impact:** Any lesson JSON generated by this script for LAB lessons would fail canonical Zod validation and the golden-path migration. Two parallel, inconsistent definitions of the same domain artifact violate the "single contract" / golden-path principle in AGENTS.md. The repo already has a correct converter (`migrate-lesson-content.ts` + `lib/content-parsers.ts`); this script duplicates and contradicts it.
- **Recommendation:** Deprecate/remove this script or route it through `lib/content-parsers.ts` and `lib/schemas/lesson-content.schema.ts`. At minimum, validate output with `validateLessonContent` before writing.

### F-SA-B32-002 — `convert-md-to-structured.ts` overwrites its input file in place with no backup
- **Severity:** Medium
- **File:** `scripts/convert-md-to-structured.ts:314-337`
- **Detail:** `outputPath = inputPath` (line 315) and the script writes back to the same `thai-g3-unit-1.json` with no backup, no dry-run, no validation gate. A parse/convert regression silently corrupts source seed data. Contrast `migrate-seed-data.ts` which creates `.backup.<timestamp>` before writing (lines 55-61, 82-85).
- **Recommendation:** Add `--dry-run`, write to a separate output, or create a backup before overwrite; validate against the canonical schema before persisting.

### F-SA-B32-003 — `create-test-users.ts` seeds privileged accounts with hardcoded weak password and no production guard
- **Severity:** High
- **File:** `scripts/create-test-users.ts:9-42, 46, 50-91`
- **Detail:** The script creates `ADMIN` and `SYSTEM` role accounts with a hardcoded, publicly-printed password `password123` (lines 28, 36, 100). There is no environment guard (e.g. refusing to run when `NODE_ENV==='production'` or unless `DEV_AUTH_ENABLED`), and it uses the shared `db` client which points at whatever `DATABASE_URL` is set. If accidentally executed against a staging/production database, it provisions known-credential admin/system users. The app's own AGENTS.md stresses "no dev overrides leaking to prod."
- **Mitigations present:** Passwords are hashed via `hashPassword` (line 46) — good, no plaintext storage. Uses `onConflictDoUpdate` for idempotency.
- **Recommendation:** Gate execution behind an explicit non-prod check; source the password from env; relocate to a clearly dev-only path. Confirm whether `pnpm seed:demo-users` (the documented path) supersedes this ad-hoc script.

### F-SA-B32-004 — Seeded test users carry no `schoolId` (tenancy)
- **Severity:** Medium
- **File:** `scripts/create-test-users.ts:50-72`
- **Detail:** `users` has a nullable `schoolId` (`packages/db/src/schema` confirms `school_id` FK). These seeded users (including TEACHER/STUDENT) are created with no `schoolId`. The repo's multi-tenancy rule scopes data by `schoolId`; tenant-less seeded accounts can behave inconsistently with FLAT-table tenant scoping and may be invisible/over-visible in tenant-scoped queries during manual QA.
- **Note:** This may be acceptable for a global smoke-test fixture, but it is a deviation worth flagging. Verify intended tenant behavior for these accounts.

### F-SA-B32-005 — `migrate-lesson-content.ts` pads alt text with spaces to satisfy `min(10)` accessibility rule
- **Severity:** Low
- **File:** `scripts/migrate-lesson-content.ts:391-394`
- **Detail:** When alt text < 10 chars, it does `alt = \`Image: ${alt}\`.padEnd(10, ' ')`. This produces meaningless padded alt text (e.g. trailing spaces) purely to pass `ImageBlockSchema.alt.min(10)` (schema line 139). It satisfies the validator but defeats the accessibility intent of the rule.
- **Recommendation:** Either surface a warning/skip for too-short alt text or carry a meaningful default rather than space padding.

### F-SA-B32-006 — `_metadata` is attached to LessonContent and persisted to DB though the schema strips it
- **Severity:** Low
- **File:** `scripts/migrate-lesson-content.ts:485-490, 556-559, 602-607`
- **Detail:** `convertMarkdownToLessonContent` mutates the object with a `_metadata` field (line 487). `validateLessonContent(lessonContent)` (line 559) returns a stripped copy (schema uses `.strip()`, schema line 260) but the **original** `lessonContent` object (still carrying `_metadata`) is what gets written to the DB (line 606 `structuredContent: lessonContent as object`). So unvalidated/extra data is persisted even though the schema intends to drop it. Behavior is inconsistent: validation result is discarded.
- **Recommendation:** Persist the validated/stripped object, or define a sanctioned metadata location.
