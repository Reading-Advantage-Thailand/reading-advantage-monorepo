## Headline

The subsystem is not one implementation. It is **two scoring implementations that
disagree**, wired to a protocol that describes a third. `ScoringEngine` — 232
lines of time bonuses, combo multipliers, and round caps — is **dead code even
inside the orphaned subsystem**: its only consumer anywhere in the repository is
`performance-benchmark.test.ts`.

## Findings, severity-ranked

### M-1 (High) — `cleanupExpiredRooms()` is never called

`room-manager.ts:181` defines it. The only references anywhere are its own
definition and tests; `ws-server.ts` never invokes it and schedules no sweep.
Rooms accumulate for the process lifetime in a `Map` that nothing drains. In the
only long-lived process this design has, that is an unbounded leak.

Note also that line 189 sets `room.status = 'expired'` and line 190 immediately
deletes the room, so the assignment is dead.

### M-2 (High) — three different trust models for one score

- The wire protocol's `ScoreSubmitMessage` carries a client-computed `score`.
- `GameSession.submitWord(playerId, word)` accepts **no score at all** and
  validates properly: player connected, word not already submitted, word present
  in `roundState.currentWords`. It then awards a flat `player.score += 100`.
- `ScoringEngine.submitWord(playerId, word, responseTimeMs)` accepts a
  **client-supplied response time** and derives a time bonus from it, guarded
  only by `responseTimeMs < 0 || responseTimeMs > 60000`. A client claiming
  `responseTimeMs: 0` takes the maximum bonus every time. The source labels this
  "Anti-cheat", which is worse than making no claim.

S1 must pick one model. The `GameSession` shape — server derives everything from
a validated word submission — is the one to keep.

### M-3 (High) — a disconnected player cannot rejoin a game in progress

`room-manager.ts:92` throws `Room ${code} is already active` for any join while
`status === 'active'`. The reconnect branch at line 100, which restores
`isConnected` and refreshes the name, is therefore **unreachable during play** —
the only phase where reconnection matters. A dropped student is out for the
match.

### M-4 (Medium-High) — room codes come from `Math.random()`

`room-manager.ts:50` builds codes from `Math.floor(Math.random() * ...)` over a
32-character alphabet. Not cryptographically random and therefore predictable
from observed codes. With no tenant or class binding anywhere in the module, a
guessed code is a join. S4's identity binding is the real mitigation; the
generator should still move to a CSPRNG.

### M-5 (Medium-High) — one fast player ends the round for everyone

`game-session.ts` ends a round when every word in `currentWords` has been
collected by **some** player:

    const allWordsCollected = this.state.roundState.currentWords.every((w) =>
      Array.from(this.state.players.values()).some((p) => p.wordsCollected.includes(w))
    );

In a race, the union across players covers the list long before any individual
finishes. The strongest player truncates the round for the rest of the class,
which inverts the intent of a race.

### M-6 (Medium) — disconnected players still occupy room capacity

`joinRoom` rejects when `room.players.size >= room.maxPlayers` (default 4), and
`leaveRoom` only sets `isConnected = false` without removing the entry. Three
departed players leave a room permanently "full" to newcomers while holding one
live participant.

### M-7 (Medium) — full state broadcast every tick, no delta

`game-session.ts` runs `setInterval` at `tickRateHz: 20` and emits a serialized
snapshot of all players on each tick regardless of change. Tolerable at four
players; it is the wrong default to promote into a platform capability, and it
sets the pattern the shared-world tier would inherit at exactly the wrong scale.

### M-8 (Medium) — a kicked player can rejoin immediately

`kickPlayer` deletes the player from the room `Map`. Nothing records the kick, so
the next `joinRoom` with the same id succeeds while the room is still `pending`.
There is no ban list or kick memory.

### M-9 (Low) — `getPlayerList` hardcodes zeros

`ws-server.ts` reports `score: 0, wordsCollected: 0` for every player. It is
reached only from `sendPlayerListUpdate`, which emits `status: 'waiting'`, so it
is **correct today** — pre-game lobbies have no scores. Recorded because the
function is named generically and will be wrong the moment it is reused for an
in-progress room. Not a defect; a trap.

### M-10 (Low) — heartbeat ratio

`HEARTBEAT_INTERVAL` 30 s against `HEARTBEAT_TIMEOUT` 90 s tolerates two missed
pings before eviction. Defensible; recorded for S4 to confirm against the
reconnect window it chooses, not to change blindly.

The single failure is
`performance-benchmark.test.ts:21` — "should calculate 1000 word scores in under
10ms", received 13 ms. It is a wall-clock threshold on an unloaded machine, not a
correctness assertion, and its subject is `ScoringEngine`, the dead module named
in the headline. It is the one test in the subsystem whose only purpose is to
exercise code nothing in production reaches. If S0's discard verdict on
`scoring-engine.ts` is taken, this file goes with it; there is no reason to tune
the threshold first.

**What the green does not mean.** 202 passing tests coexist with three High
findings, so the suite's silence is itself evidence about its shape:

- M-1 (`cleanupExpiredRooms` never called) is invisible to
  `room-manager.test.ts` because the test calls the function directly. The
  defect is the missing caller, and no test asserts a caller exists.
- M-3 (reconnect unreachable while `status === 'active'`) passes because the
  reconnect tests construct rooms in `waiting`, the one status where the branch
  is reachable and also the one where it does not matter.
- M-2 (three trust models) passes because `scoring-engine.test.ts` and
  `game-session.test.ts` each assert their own module's model in isolation. No
  test compares them, which is precisely how they came to disagree.

So the suite tests each module against itself. Every High finding lives in the
seams between modules, or between a module and its absent caller — the region
this suite does not cover. That is the gap S1's contract tests must close, and it
is a stronger argument for the contract than any failing test would have been.

subsystem defect; noted so the next runner does not chase it.

## What S1 must carry out of this audit

1. One scoring model, server-derived, no client-supplied score or response time.
2. Reconnection as a first-class state, valid during `active` play.
3. Round-end conditions expressed per player, not as a union across the room.
4. Room capacity counted over connected players.
5. Kick that persists.
6. Delta or interval-bounded state emission rather than unconditional full
   snapshots at tick rate.
7. Room identity bound to tenant and class, with codes from a CSPRNG.
