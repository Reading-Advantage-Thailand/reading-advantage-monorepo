## M-item verdicts (from the earlier review pass)

- M11 — `NOT_A_TEACHER` on move; edit dialog hides the school select for
  admin rows: STILL PRESENT, by design. `move-teacher-school.ts:63` refuses
  any `users.role !== "TEACHER"` with 400; `teachers-table.tsx:851` and
  `:210-214` render the school select only when
  `selectedTeacher?.role === "teacher"`. Spec S3 covers "teacher T" only;
  moving an ADMIN (with a `school_admins` transfer) is out of scope. Low.
- M12 — SYSTEM add-teacher dialog lists classes of all schools:
  STILL PRESENT. The add dialog (`teachers-table.tsx:531-672`) has no
  `SchoolSelect` and shares the `classrooms` state loaded unfiltered on
  mount (`:179-181` → `GET /api/classrooms`, which returns every school for
  SYSTEM). The create call sends no `schoolId` (`:223-243`), so a SYSTEM
  create makes a school-less teacher and `createTeacher` accepts any
  classroom for SYSTEM (`teacherModel.ts:453-470`, no school filter when
  `schoolId` is null). Medium — re-raised below as F2.
- M14 — move does not touch `school_admins` / `user_roles`:
  STILL PRESENT (half N/A). `move-teacher-school.ts:85-107` writes no
  `school_admins` row; `user_roles` needs no write (role is unchanged).
  A `TEACHER` row that also holds a `school_admins` row (legal per the S4
  `SCHOOL_ADMIN_ACCESS` rule) keeps a stale admin row in the old school
  after the move, and `loadTargetEffectiveRank` counts every such row.
  Medium — re-raised below as F3.
- D2 — audit insert on the transaction handle: RESOLVED for S3.
  `move-teacher-school.ts:100` uses `tx.insert(auditEvents)` inside the
  move transaction (a bad actor id rolls the whole move back, as
  `acceptance.md` records). `recordAuditEvent` itself still uses the global
  handle (`packages/auth/src/audit.ts:84`); S5 (`teacherModel.ts:827-836`)
  and S2 (`import-school.ts:60-63`) call it after commit as documented
  best-effort. Residual is Low — see F5.
