## 5. Merge rules

- Who merges: only the Monorepo session merges into local master. A push of master and any deploy need Daniel's go. Every app builds from master. A subject merge changes the Primary build only when it changes a shared package that Primary uses. The A-21 track metadata names the Monorepo orchestrator as the owner of the merge to local master (`measure/tracks/security_upgrade_20261026/metadata.json`).
- When: at a phase boundary, after the subject phase passes its Measure phase acceptance gate on the branch HEAD. Send a merge request to the Monorepo session with the branch, the HEAD SHA, the accepted phase, and the gate evidence.
- Gates before the request:
  - (a) Merge current master into your branch and resolve every conflict on your branch. (b) Rerun, through `heavy-run.sh`, `check-types`, `lint`, `test`, and `build` for the subject app, for each shared package that you changed, and for `primary-advantage` when a changed package is one that Primary uses.
  - (c) The tenant-coverage test in `packages/domain` passes. (d) After A-21 merges, `tests/security-upgrade-version-guard.test.ts` passes, so no dependency falls below an A-21 floor. That test file does not exist yet. It arrives with A-21.
  - (e) No new failure compared with master. A check that fails on master too is listed with its master log. (f) A clean worktree, Conventional Commits with `(track_id: <id>)`, and a header of 100 characters or less.
- Merge order:
  1. A-21 security upgrade, expected 2026-10-30, because it changes `pnpm-lock.yaml` for every app. The A-21 track metadata records a due date of 2026-10-27 (`measure/tracks/security_upgrade_20261026/metadata.json`).
  2. Storytime commits, which land on master directly.
  3. Subject branches one at a time, the first ready branch first. For a tie, Science, then Math, then Zhongwen.
- After each merge, the other subject sessions merge master into their branch before their next request.
